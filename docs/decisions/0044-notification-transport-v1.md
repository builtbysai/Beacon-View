# ADR 0044: Deliver opt-in notification transport through PostgreSQL

Status: Deployed to the Oracle private alpha on September 12, 2026; Chrome Web Push
acceptance passed, while native FCM and the remaining physical matrix stay gated.

## Context

ADR 0043 established Firebase and Web Push boundaries without enrolling users. Beacon now needs a complete subscription and delivery lifecycle before either provider can be activated. Push identifiers can address an installation, background delivery can expose information on a lock screen, and offline detection can become noisy if it treats every missed heartbeat as an event.

## Decision

- PostgreSQL remains the only application source of truth. Store subscriptions, per-camera preferences, transition events, presence state, and a transactional delivery outbox there.
- Use current Firebase Installation IDs through `register`, `onRegistered`, and `unregister`; do not build new behavior on deprecated FCM registration-token APIs. Send Android data-only messages to the HTTP v1 `fid` target.
- Encrypt provider identifiers/endpoints with a random per-record AES-256-GCM data key wrapped by a separately managed AES-256-GCM server key. Use a different HMAC key only for idempotent equality checks.
- Bind every subscription to its authenticated Beacon account session and installation. Logout, session revocation, account deletion, explicit opt-out, and permanent provider invalidation stop delivery.
- Default every camera preference off. Users separately enable motion and offline/recovery alerts. One daily IANA-time-zone quiet interval suppresses both categories.
- Treat one physical host device as one offline target. The established 90-second presence window plus a 120-second grace produces at most one offline event and one corresponding recovery event. Privacy, disabled, revoked, deleted, and never-seen devices do not alert.
- Create motion notification events and outbox rows in the same transaction as accepted motion metadata. A bounded worker uses PostgreSQL row leases, retry backoff, and provider-invalid cleanup; no Redis or additional service is introduced.
- Payloads contain only a version, opaque event ID, category, and generic route. Android and the service worker own fixed generic copy. Opening an alert reopens Beacon and re-fetches authorized state.

## Consequences

The implementation is inert without application encryption keys and provider configuration. No sender credential or VAPID private key is committed or generated by this change. Real delivery, Doze behavior, uninstall cleanup, installed-PWA behavior, and provider response classification remain manual evidence gates before release.

Security alerts remain deferred with the account-recovery milestone. Household sharing, recordings, Google Drive integration, and viewer-count repair are separate milestones.
